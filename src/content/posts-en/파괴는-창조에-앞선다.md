Hacking happens on top of systems that have already been built.

And security develops from discovered vulnerabilities.

In other words, attacks on vulnerabilities always come first, and responses follow.

<p class="rilog-empty-block" aria-hidden="true"><br /></p>

<strong>Building a system that cannot be attacked is impossible.</strong>

Developers need to build <strong>systems there is no reason to attack</strong>, rather than systems that cannot be attacked.

<p class="rilog-empty-block" aria-hidden="true"><br /></p>

<strong>And I have reason enough.</strong>

## When does a Rilog view count go up?

The `GET` request that reads a post's detail page is separate from the request that registers a view.

The frontend sends the following request when someone actually enters the detail page.

```http
POST /v1/posts/222/views
```

The backend uses a member ID to identify logged-in visitors, and the UUID in the `rilog_visitor` cookie to identify guests.

If a guest has no cookie, it creates a new UUID and sends it back in a cookie.

When the same identifier accesses the same post again, it treats the visit as a duplicate for one hour after the last counted view.

When an author logs in and views their own post, the view count does not increase.

<p class="rilog-empty-block" aria-hidden="true"><br /></p>

<strong>What if the request comes from a program that does not retain cookies, rather than a browser?</strong>

## One cookie is not one person

```bash
curl -i -X POST 'https://api.rilog.kr/v1/posts/222/views' \
  -H 'Origin: https://www.rilog.kr' \
  -H 'Content-Length: 0'
```

The production API returned `204 No Content` and a new `rilog_visitor` cookie.

The behavior of the code issuing a new guest identifier was visible in the actual response, too.

Unless you specify a separate cookie store, `curl` does not automatically send a cookie received in a response with the next request. Run the same command again, and the server receives another request without a cookie.

The server issues another new UUID, which has no record of reading this post.

## Why there is no need to wait an hour

Duplicate views are identified by neither IP address nor browser. The criterion is <strong>the combination of post ID and visitor identifier</strong>.

If a guest request has no `rilog_visitor` cookie, the server creates a new UUID.

There is no record of that UUID viewing the post. So there is no previous timestamp to compare when checking the one-hour limit.

The workaround is simply to <strong>leave the issued cookie out of the next request.</strong>

```python
from urllib.request import Request, urlopen

url = "https://api.rilog.kr/v1/posts/222/views"

for _ in range(3):
    request = Request(url, data=b"", method="POST")

    with urlopen(request, timeout=15) as response:
        print(response.status, response.headers.get("Set-Cookie"))
```

<p class="rilog-empty-block" aria-hidden="true"><br /></p>

<strong>The server's logic as requests repeat</strong>

1. There is no cookie.
2. Issue a new UUID.
3. There is no view record for this UUID.
4. Count the view and return a cookie in the response.
5. The client does not retain the cookie.

The next request starts from step 1 again.

Even as you read this post, the view count is going up.
