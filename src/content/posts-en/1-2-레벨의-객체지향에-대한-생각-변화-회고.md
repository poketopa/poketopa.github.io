## Level 1
I hear all the time that object orientation is good for maintainability.
I can also explain why dividing responsibilities, reducing dependencies, and using immutable objects is good.
But I do not really understand why I should write my code that way right now.
While preparing for the Level 1 interview, I wrote quite honestly about that feeling.

> My honest answer to why I introduced so many layers and split classes apart is roughly, "Because everyone did, and because we were encouraged to."

That does not mean I had learned nothing. I could explain the reasons I had been taught, but those reasons were not yet part of my own experience.

## What object orientation meant to me

The constraints in the Blackjack and Janggi missions felt like the rules of soccer. If you ask why you cannot use your hands in soccer, the answer is that this is what makes it soccer. Object-oriented design felt similar to me.

If I could make a working program, why did I need to divide it up this much? It felt as though I was deliberately following difficult rules when there was a simpler way to write it now.

While building Blackjack, I focused on implementing it quickly. For tests, I also thought it would be nice to locate failures quickly. Along the way, I reconsidered code that cleared global state before tests, let cards choose random values themselves, or put domain objects inside DTOs.

When each issue was explained, I understood why it could be a problem. But understanding did not immediately make me want to avoid writing that kind of code in the first place.

Perhaps I could have directly compared the approach I found convenient with the recommended one. That occurred to me while writing my interview answers, too. I wrote that I disliked simply following what everyone said was good, yet probably had not been diligent enough to prove my own thinking. It is a little embarrassing, but it describes who I was then quite well.

In my Blackjack retrospective, I looked at myself more sharply. I wrote that I had been cynical, asking why we had to do things this way when there were so many tedious steps and performance seemed worse. I said this probably reflected an attitude of finding learning bothersome, rather than being a developer who valued performance. I think even I could not clearly distinguish wanting to be convinced from not wanting to learn.

## Level 2

In Level 2, new things arrived all at once. I thought about how to write tests and how many changes to group into a transaction. Meanwhile, I did not think enough about domain responsibilities. Just getting the code working and applying newly learned technologies already demanded a lot of attention.

But as features were added one by one, the same decisions had to be made in multiple places. The code grew, duplication increased, and I became increasingly unsure where to make changes.

Looking together at the code left after review in two cycles reveals traces of those concerns. In reservation waiting cycle 1, the service performed validation, saving, and queue position lookup in sequence.

```java
@Transactional
public WaitingResponse save(WaitingRequest body, long memberId) {
    slotService.validateSlot(body.date(), body.timeId(), body.themeId());
    long slotId = slotService.resolveSlotId(body.date(), body.timeId(), body.themeId());

    validateReservedByMemberNotExists(memberId, slotId);
    validateWaitingByMemberNotExists(memberId, slotId);
    validateWaitingTargetExists(slotId);

    Waiting waiting = waitingRepository.save(body.toDomain(memberId, slotId));
    long waitingOrder = waitingRepository.countBySlotIdAndIdLessThanEqual(slotId, waiting.getId());

    return WaitingResponse.of(waiting, waitingOrder);
```

In the next cycle, a `WaitingLine` appears, grouping waitlist entries for the same slot and determining their order. One of its methods looks like this.

```java
public long orderOf(Waiting waiting) {
    for (int index = 0; index < waitings.size(); index++) {
        if (hasSameId(waitings.get(index), waiting)) {
            return index + 1L;
        }
    }
    throw new IllegalArgumentException("대기열에 존재하지 않는 대기입니다.");
}
```

These are not before-and-after versions of the exact same method moved elsewhere, but they still show where I was considering placing responsibility. What initially involved assembling query results in the service later became a question I could ask the waiting line itself.

In my final retrospective on June 5, I wrote this.

> In Level 1, I thought about domain responsibilities and designed them "because I was told to." But in Level 2, I experienced how my weak domain design caused large amounts of code to appear whenever features were added, leaving it duplicated, tangled, and difficult to manage.

## Must I be convinced before I can learn?

I have not belatedly accepted every Level 1 constraint as the correct answer. It is still difficult to decide how far to divide things or which responsibilities belong together.

But I think I used to believe that understanding an advantage should immediately make me feel its necessity. If I did not feel it, I questioned the rule or thought I had failed to learn properly.

Yet the point at which I understood an explanation and the point at which I urgently needed it seem to have been different. Only after experiencing the difficulties of Level 2 did the things I heard in Level 1 become words of my own.

That is why I have come to think that learning something whose necessity I do not yet feel is not entirely pointless.
