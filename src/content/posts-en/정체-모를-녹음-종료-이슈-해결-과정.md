## The problem

We kept encountering <strong>recordings ending even though the user had not pressed the stop button</strong>.

The server logs recorded `CONNECTION_EXPIRED`. <br />This meant the recording had ended because the heartbeat—the browser's sign of life—had stopped arriving. <br />At the time, we <strong>found 29 such terminations</strong> in the preceding 14 days of records.

We tried to reproduce these errors, but finding the cause was not easy.

This post describes how investigating the connection loss led us first to change our policy for handling recordings when a connection drops.

## 1\. Connections dropping for unknown reasons

The description we repeatedly received from users was `I had not closed my laptop, and Chrome was still open, but the recording suddenly ended.`

Looking into it, we found several possible explanations:

- Delayed timers in background tabs
- The browser suspending a tab or reclaiming memory
- The browser spending a long time on other work
- A temporary request failure

The network might have dropped, or the user might have closed the tab. We also considered the device going to sleep or the influence of browser settings and policies. But the server records we examined did not let us distinguish among these causes.

## 2\. Separating connection status from recording termination

To solve this, we needed a policy that ended recordings for users who closed the tab and left (the normal termination flow), while letting users whose internet briefly dropped continue the same recording.

Our first thought was to extend the heartbeat timeout, but we still needed to tell users when the connection dropped and eventually end recordings whose users never returned. <br />So, together, the team defined separate <strong>criteria for indicating disconnection and for ending a recording</strong>.

| Situation | Revised policy |
| --- | --- |
| No sign of life for 30 seconds | Mark as disconnected without immediately ending the recording |
| User returns within 30 minutes of the last sign of life | Allow the same recording to resume |
| No sign of life for 30 minutes | End the recording |

These thresholds were intended to allow room for the connection to return without waiting indefinitely.

![](/images/rilog/359/01.webp)

We also stopped judging connectivity by heartbeat alone. <br />If requests to schedule or complete an audio upload were arriving, the browser was communicating with the server, so we <strong>included audio upload requests when updating the last-seen-alive time</strong>.

### Distinguishing this from normal termination

Knot does not allow one member to start multiple recordings simultaneously. Merely extending the grace period could leave someone who closed the tab and returned unable to start a new recording for up to 30 minutes.

So we kept the ability to end an existing recording from another tab. People who wanted to continue an existing recording got time to return, while people who wanted a fresh start could explicitly end it and begin again.

## 3\. How can returning users resume the same recording?

Under the revised policy, users needed to be able to continue an existing recording even after refreshing the same tab. <br />We added two policies for this.

### Allowing only the new page to control the recording

A recording resumed on a new page must not be ended again by a termination request from the old page. So, on resumption, we <strong>replaced the control token and rejected requests using the previous token</strong>. Only requests from the new page could change the recording's state.

![](/images/rilog/359/02.webp)

### Resending from the first unsaved audio

Next, we decided where audio should start being resent. Even if an upload had been scheduled, the actual file might not have been stored.

For example, if chunks 1 and 2 were stored but 3 was missing, we needed to receive again from 3 even if 4 was stored. So we <strong>checked how far audio had been saved without gaps from the beginning, and resumed sending from the next point</strong>.

We stop at the first chunk whose sequence number or audio position is not continuous, or whose storage has not been confirmed. This lets us resume without skipping missing audio in the middle.
