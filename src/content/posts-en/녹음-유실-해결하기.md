## The problem

While improving transcription quality, we received feedback that `the recording itself was lost`.<br />There were indeed many cases of recordings lost when browsers closed, and we also found users who never returned afterward.<br />For a recording service, losing the original recording file was a truly critical problem.

We believed users needed <strong>confidence that their recordings would remain</strong> before entrusting their next meeting to Knot.<br />So we changed the approach of saving only when a recording ended, and enabled failed processing to restart from saved audio.

## 1\. Save before the recording ends

Previously, the browser collected audio and uploaded it all at once after recording ended.<br />But if the tab closed before upload, the file was lost and nothing remained on the server.

We needed to retain the audio recorded so far even if the user could not press the stop button.

So we changed the browser to <strong>split the audio every five seconds and save it to S3</strong>. We received audio in `PCM` format so it could be concatenated in order.

![Saving the original in chunks during recording](/images/rilog/357/01.webp)

## 2\. Verify that the file was actually saved

The browser sent files directly to S3, reducing the burden of having the backend receive and retransmit large audio files.

Could we then start transcription as soon as the browser reported that upload was complete?

The uploaded content could differ from the reserved file, or the same request could arrive again. So we <strong>separated upload reservation from confirmed storage</strong> and checked the actual file on the server.

![Upload reservation and storage verification](/images/rilog/357/02.webp)

The browser first reserves an upload with a sequence number, audio location, size, and `SHA-256` checksum. When a completion request arrives, the backend compares the S3 object's size and checksum and saves the version of the matching file in the DB.

We retained the file version because content at the same path could change later. Transcription also specifies that version to read <strong>the original whose storage we had verified</strong>.

A repeated request with the same sequence number and content returned the existing result. Requests with the same number but different content were rejected, preventing retries from adding chunks or mixing in different audio.

### What if the state changes while waiting for S3?

Waiting for an S3 lookup inside a DB transaction could hold locks for a long time if the external response was slow.

So we <strong>performed S3 lookups outside the transaction</strong>. When finalizing storage afterward, we checked the recording state and control permissions again. Even if they were valid when the request arrived, they could change while we waited.

The code, too, separates preparing verification, looking up S3, and finalizing storage.

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public RecordingAudioChunkCompletionResult complete(
        long workspaceId, long memberId, long recordingId,
        int sequence, RecordingControlCommand command
) {
    RecordingAudioChunkConfirmation preparation = transaction.prepareConfirmation(
            workspaceId, memberId, recordingId, sequence, command);
    if (preparation.completed() != null) {
        return preparation.completed();
    }
    StoredAudioChunk stored = storage.findStoredObject(preparation.storageKey());
    return transaction.confirmStored(
            workspaceId, memberId, recordingId, sequence, command, stored);
}
```

## 3\. Resuming failed processing

Even with the original saved, the AI server could stop, or transcription could finish without its result being saved. We felt preserving the original would be pointless if users still had to record again.

We recorded jobs and their progress in the DB, assigning an ID to each execution attempt. If an AI response was missed, we <strong>queried the status and result of the same attempt first</strong>. We fetched and saved completed results, and only resubmitted the same original after confirming the AI had no such job.

Creating a new job immediately upon receiving no response could duplicate a transcription the AI was already running.

### What if a stalled worker returns late?

We gave workers ownership and an expiration time, allowing another worker to take over if renewals stopped.

But we also had to consider A returning with a result after stalling and handing work to B. If both could save, results for the same job could conflict.

So we changed a <strong>generation number</strong> whenever a job was handed over. Saving a result requires <strong>both the current owner and the generation number to match</strong>.

![Job ownership transfer and blocking the previous worker from saving](/images/rilog/357/03.webp)

After B takes over, A's late save is rejected.

Before applying results, we check these conditions.

```java
public boolean isOwnedBy(UUID attempt, UUID owner, long epoch, Instant now) {
    return isProcessingAttempt(attempt)
            && owner != null && owner.equals(ownerToken)
            && epoch == claimEpoch
            && leaseUntil != null && now.isBefore(leaseUntil);
}
```

We also bundled saving the transcription and accepting the next document-generation task into <strong>one transaction</strong>, to avoid leaving users waiting after a transcription was saved but document generation was omitted.
