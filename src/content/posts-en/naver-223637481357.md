## 1. Introduction

## 1.1 Purpose

The purpose of this report is to design and verify a Diffie-Hellman key exchange protocol that lets three users—Alice, Bob, and Carol—generate a common secret key and safely share a secret message.

The users publicly select a generator g for a group G, and privately select random numbers n0, n1, and n2 respectively. Once they agree on a common secret key, Alice must encrypt a secret message s using that key and send it to Bob and Carol.

Using ProVerif, we configure passive and active attackers and analyze whether communication can remain secure under each attack model.

## 2. Basic Protocol Design (Passive Attacker)

## 2.1 Protocol overview

The protocol aims to let Alice, Bob, and Carol generate a shared key over public channels and use it to exchange a secret message.

A passive attacker can eavesdrop on communication, but cannot manipulate messages or key values.

ProVerif provides an exp function for exponentiation, but because it only supports exponentiation between the G and exponent types, additional data exchanges are needed for all three users to obtain a common secret key.

## Implementation:

Alice, Bob, and Carol share the values gx, gy, and gz with each other, obtaining the intermediate values they need (gxy, gxz, gyz).

The intermediate values are combined with Alice, Bob, and Carol's n values using exp to obtain the value needed for the shared key (gxyz).

The final shared key is calculated through this staged computation, implemented to overcome the constraints of ProVerif's exp function.

## 2.2 Description of each process

Alice's process:

Alice chooses her private exponent n0, calculates gx, and sends it to Carol and Bob.

She calculates the shared key using gyz received from Carol.

Bob's process:

Bob chooses his private exponent n1, calculates gy, and sends it to Carol.

Bob uses gx received from Alice to calculate gxy and sends it to Carol.

He calculates the shared key using gxz received from Carol.

Carol's process:

Carol chooses her private exponent n2 and calculates gz.

Using gx and gy received from Alice and Bob, she calculates gxz and gxy and sends them to Alice and Bob.

She calculates the shared key using gxy received from Bob.

## 2.3 Encryption and decryption

Encryption:

Alice encrypts the secret message using the shared key and sends it to Bob and Carol.

The encryption function enc and decryption function dec are used in this process, with the shared key as the key value for transmitting the secret message.

Decryption:

Bob and Carol use the shared key to decrypt the encrypted message and read the secret message.

## 3. Adding Digital Signatures and Defending Against an Active Attacker

## 3.1 Active attacker scenario

An active attacker can manipulate messages or the key exchange process.

Attacks such as message tampering and key forgery are possible, so encryption alone cannot guarantee communication integrity.

We therefore let each participant use digital signatures to demonstrate the integrity of the message's sender.

## 3.2 Implementing digital signatures

Private and public keys: define private and public keys for Alice, Bob, and Carol respectively, and use them for signing and verification.

Signing and verification functions:

The sign function signs a message with a private key, demonstrating that it was sent by the legitimate sender.

The verify function verifies a signed message with a public key to identify the signer and confirm that the message has not been altered.

## 3.3 Signature verification in each process

Processes

Apply the signing function to all data sent by Alice, Bob, and Carol.

When Alice, Bob, and Carol receive data, they verify it with the public key to identify the signer and check message integrity.

Through signatures, each participant verifies that a received message has not been tampered with and comes from a trusted participant.

## 4. Code Explanation

## 4.1 Code for a passive attacker

Attacker configuration:

This code assumes only a passive attacker. The attacker can eavesdrop on communication, but cannot alter messages or values.

Consequently, signing and verification are not implemented; only key exchange between participants and transmission of encrypted messages are implemented.

## 1. Channel definitions

channel_ab: a channel for communication between Alice and Bob.

channel_ac: a channel for communication between Alice and Carol.

channel_bc: a channel for communication between Bob and Carol.

Each channel transfers data between participants, sending and receiving particular data through out and in statements.

## 2. Function definitions

enc(bitstring, G): bitstring:

A function encrypting a secret message. It uses type G (the shared key) to encrypt a message (bitstring), returning the encrypted bitstring.

dec(bitstring, G): bitstring:

A function decrypting an encrypted message. It uses the shared key (type G) to recover the original message (bitstring).

A reduc rule establishes how encryption and decryption interact to recover the original message.

exp(G, exponent): G:

An exponentiation function that generates a value of type G using the public generator G and a private exponent (type exponent).

Each participant uses values generated by exp in the calculations deriving the shared key.

## 3. Generators and constants

g: G:

The public generator used by Alice, Bob, and Carol. Each combines this value with a private exponent to generate the shared key.

ok: bitstring, not_ok: bitstring:

Constants for message verification, indicating that a message was decrypted correctly.

## 4. Variables

Private exponent variables:

n0: Alice's private exponent.

n1: Bob's private exponent.

n2: Carol's private exponent.

Variables for shared-key calculation:

gx, gy, gz: values each participant obtains by exponentiating the public generator g with their own private exponent.

gxy, gxz, gyz: intermediate results needed for shared-key calculation between participants, ultimately exponentiated with a private exponent to obtain shared_key.

shared_key: the final shared key, calculated by Alice, Bob, and Carol by combining their private exponents with values received from other participants.

Secret message variable:

s: the secret message Alice sends to Bob and Carol, encrypted with the shared key before transmission.

## 4.2 Code for an active attacker

Attacker configuration:

This code assumes an active attacker, adding digital signing and verification to defend against an attacker capable of manipulating communication.

## Elements added in the active code

![Diffie Hellman Key Exchange Protocol Analysis image 6](/images/naver/naver-223637481357-6.webp)

## 1. Functions

sign(bitstring, privKey): bitstring:

A function that signs a bitstring message with a private key (privKey) for transmission.

Each participant can use this function to demonstrate that their sent message has not been altered.

verify(bitstring, bitstring, pubKey): bitstring:

A function that receives a signed message and public key (pubKey) and checks message integrity.

It returns ok on successful verification and not_ok on failure.

to_bitstring(G): bitstring:

A function converting a value of type G into a bitstring, converting values needed for signing and verification into bitstring form so they can be signed.

It allows the result of exp to be passed to sign.

## 2. Constants

ok: bitstring:

A constant indicating successful verification, returned when verify successfully verifies a signature.

not_ok: bitstring:

A constant indicating verification failure, returned when verify cannot verify a signature.

## 3. Private and public keys

Private keys:

Each participant's private key is used to create digital signatures. Alice, Bob, and Carol use these private keys to sign outgoing messages and demonstrate their integrity.

Public keys:

Each participant's public key is used to verify signatures. Alice, Bob, and Carol use each other's public keys to verify signatures on incoming messages and check whether they came from a trusted participant.

Process description (Carol's process):

Digital signatures: create and verify digital signatures for all communication exchanged by Alice, Bob, and Carol.

Verification: verify the signature whenever data is received, terminating the process if the message's source is unclear.

## 5. Verification Results Using ProVerif

## 5.1 Verification against a passive attacker

![Diffie Hellman Key Exchange Protocol Analysis image 8](/images/naver/naver-223637481357-8.webp)

Verification process:

We simulated a situation in which communication can be intercepted using ProVerif's passive attacker setting.

The ProVerif results confirmed that the attacker could not access the secret message or shared key. However, because a passive attacker does not manipulate or damage messages, this cannot tell us whether protocol integrity was preserved.

Verification result:

A shared key was generated between Alice, Bob, and Carol, and they successfully decrypted the secret message.

## 5.2 Verification against an active attacker

![Diffie Hellman Key Exchange Protocol Analysis image 9](/images/naver/naver-223637481357-9.webp)

Purpose: in the active attacker model, verify whether message integrity and identity are preserved with digital signatures even when an attacker manipulates communication.

Verification process:

We simulated an attacker able to intercept and manipulate communication using ProVerif's active attacker setting.

Through sign and verify, participants signed each message and key exchange and checked each signature's validity.

We verified that an attacker could not alter signed messages or key values during message transmission and verification, and confirmed that attempted tampering caused verification to fail because of an invalid signature.

Verification result:

The protocol with digital signatures maintained communication integrity under the active attacker model.

According to the ProVerif results, even if an attacker alters a message, verification identifies it, guaranteeing the protocol's integrity.

## 3 Channels, Signature X

```
free channel_ab: channel.
free channel_ac: channel.
free channel_bc: channel.

type G.
type exponent.

set attacker = passive.

fun enc(bitstring, G): bitstring.
reduc forall x: bitstring, y: G; dec(enc(x, y), y) = x.

const g: G.
fun exp(G, exponent): G.
equation forall x: exponent, y: exponent; exp(exp(g, x), y) = exp(exp(g, y), x).

free s: bitstring [private].
query attacker(s).

(* Alice 프로세스 *)
let p0 = new n0: exponent;
let gx = exp(g, n0) in
out(channel_ac, gx);

in(channel_ac, gyz: G);
let shared_key = exp(gyz, n0) in

out(channel_ab, gx);

let encrypted_message = enc(s, shared_key) in
out(channel_ab, encrypted_message);
out(channel_ac, encrypted_message).

(* Bob 프로세스 *)
let p1 = new n1: exponent;
let gy = exp(g, n1) in

out(channel_bc, gy);

in(channel_bc, gxz: G);
let shared_key = exp(gxz, n1) in

in(channel_ab, gx: G);
let gxy = exp(gx, n1) in

out(channel_bc, gxy);

in(channel_ab, encrypted_message: bitstring);
let s_bob = dec(encrypted_message, shared_key).

(* Carol 프로세스 *)
let p2 = new n2: exponent;
let gz = exp(g, n2) in

in(channel_ac, gx: G);
let gxz = exp(gx, n2) in

in(channel_bc, gy: G);
let gyz = exp(gy, n2) in

out(channel_ac, gyz);

out(channel_bc, gxz);

in(channel_bc, gxy: G);
let shared_key = exp(gxy, n2) in

in(channel_ac, encrypted_message: bitstring);
let s_carol = dec(encrypted_message, shared_key).

process p0 | p1 | p2
```
